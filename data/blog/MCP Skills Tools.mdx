# Function Calling

Function Calling 也叫 Tool 出现的意义就是解决大模型只会说话的问题。
大模型

1. 无法感知环境：无法与外部数据源交互，API 查询网页、查看用户本地文件、访问远程数据库等
2. 无法改变环境：无法修改文件、跑代码、上传作业等

我们不难发现，这不正是一些后端做的事吗？

1. 从数据库中读取一点数据
2. 将一些东西写入文件
3. 发送一些请求

这都是后端做的事。

## 如何解决

以查询天气举例：

![传统方式：程序用正则和字符串匹配调用查天气函数](/static/images/MCP/image.png)

我们能发现，为什么不让 AI 来取代正则和字符串匹配？让 大模型来填写后端的参数？

## 方案

广义的`Function Calling`是指大模型能够调用外部工具的一种技术实现，先
向大模型提供可用函数的列表及说明，由大模型在对话过程中智能判断是否需要调用函数，并自动生成调用所需的参数，最终用文字返回符合约定格式的函数调用请求。

狭义的 Function Calling 特指大模型提供商在模型内部与 API 层面做了支持的一种能力，它最早由 OpenAI 引入：

- 在模型层面：模型提供商需对大模型进行特别优化，使其具备根据上下文正确选择合适函数、生成有效参数的能力（比如有监督微调、强化学习）。
- 在 API 层面：模型提供商需额外开放对 Function Calling 的支持（比如 GPT API 中提供了一个 functions 参数）。

![Function Calling 工作流程：函数描述写在系统提示词里](/static/images/MCP/FunctionCalling.png)

```
# 你的角色

你是一个函数调用助手，我将提供多个函数的定义信息，包括函数名称、作用、参数及参数类型。

# 你的任务

- 根据用户的输入，判断是否需要调用某个函数
- 如果需要，请**严格按照以下格式**输出函数调用指令：


{ "name": "函数名", "arguments": { "参数名": "参数值" } }


# 函数定义信息

1. **get_weather**
   - 作用：查询指定城市的天气情况
   - 参数：
     -`city`（string）：城市名称
2. **get_time**
   - 作用：查询指定城市的当前时间
   - 参数：
     - `city`（string）：城市名称

“广州的天气怎么样？”
{ "name": "get_weather", "arguments": { "city": "广州" }}

```

## 存在的问题

1. 输出格式不稳定。如调用指令中存在多余自然语言。
2. 容易出现幻觉。模型可能编造并不存在的函数名或参数。
3. 对开发者依赖度高。函数描述、调用指令格式、提示词逻辑完全由开发者设计。
4. 4. 上下文冗长，Token 消耗大。为确保调用逻辑正确，往往需要在 system prompt 中加入大量说明与规则。

![API 层面的 Function Calling：函数描述放进模型 API 的指定字段](/static/images/MCP/APIFunctionCalling.png)

函数描述

```json
{
  "messages": [
    {
      "role": "system",
      "content": "你是一个助手，可以根据用户的请求调用工具来获取信息。"
    },
    {
      "role": "user",
      "content": "广州今天天气如何？适合出门吗？"
    }
  ],
  "functions": [
    {
      "name": "getWeather",
      "description": "获取指定城市的天气",
      "parameters": {
        "type": "object",
        "properties": {
          "location": {
            "type": "string",
            "description": "城市名称，比如北京"
          },
          "date": {
            "type": "string",
            "description": "日期，比如 2025-08-07"
          }
        },
        "required": ["location", "date"]
      }
    }
  ]
}
```

函数调用指令

```json
{
  "function_call": {
    "name": "getWeather",
    "arguments": {
      "location": "Guangzhou",
      "date": "2025-07-17"
    }
  }
}
```

后端解析模型返回的调用指令后，得到函数名称和参数，执行对应方法

### 存在的问题

1. 后端应用适配不同大模型时存在大量冗余开发
2. 可选模型有限

# MCP 协议

解决什么问题：

1. 工具接入的冗余发开问题： 使用别人开发的工具需要完整的 copy 代码和函数
2. 工具复用问题：环境适配问题，不开源问题，跨语言问题

理想的解决方法：

1. 开发一个 Tool 包，给别人导入调用就行 1. 跨语言问题解决不了？难道每个语言写一个包？
   难道解决不了跨语言的问题吗？
   方法： 本地服务：起一个进程运行该语言的执行环境、工具代码原封不动运行在对应语言中，AI 应用再通过进程间通信获取标准化结果。

2. 远程服务，类似 API 封装，远程调用工具，规定请求格式/响应格式。无需关注语言、环境、内部逻辑
   可行

有没有更简单的方法？让开发者只需要加一个配置就能接入别人的工具？

- 当前每新增一个工具，开发者需要在链路中做两处人工适配：
  1. 补充工具描述
  2. 补充工具代码

从非理想状态到理想状态必须满足什么条件？

- 要让“配置替代人工适配”，必须满足以下两点：
  - 新增配置后，AI 应用后端要能根据配置自动获取工具的描述信息
  - 新增配置后，AI 应用后端要能根据配置自动定位工具调用入口并执行调用

## 技术方案思路

1. 工具与AI 应用必须解耦合。
2. 工具与AI 应用之间的交互必须标准化。
3. AI 应用和工具服务的通信协议需要统一（本地进程间的通信协议 / 远程服务调用的协议）
4. AI 应用和工具服务的接口定义需要统一（需要提供哪些接口、接口需包含哪些参数）
5. AI 应用和工具服务的数据交换格式需要统一（接口的请求 / 响应格式等)
6. AI 应用接入工具的配置内容需要进行标准化定义
7. 所有工具服务必须提供标准化的接入方式，以支持通过标准化配置即可加载工具
8. 所有 AI 应用内部需实现标准化的工具加载调用逻辑，以支持通过标准化配置即可加载工具

## 什么是 MCP 协议？

MCP 是一个开放协议，用于标准化应用程序向大语言模型（LLM）提供上下文的方式。你可以把 MCP 想象成 AI 应用的 USB-C 接口——正如 USB-C 提供了一种将设备连接到各种外设和配件的标准化方式一样，MCP 提供了一种将 AI 模型连接到不同数据源和工具的标准化方式。借助 MCP，你可以在 LLM 之上构建智能体和复杂工作流，并将你的模型与外部世界相连接。

## MCP 核心架构

可以说是比较经典 Client Server 架构

分为

1. MCP Host：协调和管理一个或多个 MCP Server 的人工智能应用程序
2. MCP Client：一个组件，用于维护与 MCP 服务器的连接，并从 MCP 服务器获取上下文，供 MCP 主机使用
3. MCP Server：一个为 MCP Client 提供上下文的程序

我们可以说 VSCode 作为 MCP Host 与 MCP Server 创立链接，实例化维护与 Sentry MCP 服务器连接的 MCP 客户端对象/

## Stdio 传输

stdio - 进程的标准输入/输出接口。每个进程启动时，操作系统会给它分配 三个文件描述符：

```
0 → stdin  （标准输入，默认是键盘）
1 → stdout （标准输出，默认是屏幕）
2 → stderr （标准错误输出，默认是屏幕）
```

程序里的 printf、scanf、cin、cout、read、write 都是通过这些接口和外界交换数据的。

管道: 管道是操作系统内核提供的一种进程间通信（IPC）机制，它允许一个进程的输出直接作为另一个进程的输入，实现数据在两个进程之间的流动。

所谓 Stdio 传输，就是通过标准输入和标准输出这两个数据流来传输数据、通过管道来连接两个进程的标准输入/输出接口，使得一个进程的输出直接传给另一个进程输入，实现进程间数据传输（本质上是一个基于字节流的全双工通信通道）

旧方案是 HTTP + SSE 传输

新方案是 Streamable HTTP 传输
