# 历史渊源

我们知道 React 主要由两个关键部分组成：协调器（_reconciler_）与渲染器（_renderer_）。

在 React 中，渲染器是可插拔的，可以换成社区的渲染器，但协调器只有一个。

React 16 将协调器从 Stack Reconciler 换成了 Fiber Reconciler。

## 带来了什么？

首先是更新的优先级：

- 用户用键盘输入内容时，需要立即得到反馈，这是高优先级。
- 而像服务器返回的数据，比如评论的点赞数，这是低优先级。

再以动画举例：
流畅的动画需要 60FPS，也就是每 16ms 更新一帧。
但一些比较复杂的更新往往超过 16ms，导致动画卡顿，而且时间主要花在渲染上，而非协调上。
所以单纯让 React 跑得快一点，并不能解决问题。

Fiber 带来的是一套如何拆分工作、如何按优先级处理工作的方法。

## 比较

Stack Reconciler 按 Elements -> Instances -> DOM 的路径，从根节点一路处理到最深层节点。
这个过程像递归一样，多个执行上下文压在 Call Stack 上，浏览器根本没有时间去检查是否有其他工作需要执行。

![CallStack](/static/images/Fiber/image.png)

而 Fiber 则不同：

![Fiber](/static/images/Fiber/fiber.png)

Fiber 是一个普通的 JS 对象。Fiber 之间通过 `child`、`sibling`、`return` 三个指针连接，如图：

![Fiber 关系](/static/images/Fiber/relationship.png)

可中断更新主要指的是 Phase 1：Render / Reconciliation 阶段，Phase 2：Commit 阶段不能中断。

![Update](/static/images/Fiber/Update.png)

1. `setState` 被调用时，会创建一个 `update` 对象并加入更新队列。
2. React 安排工作，根据优先级决定是否需要立即更新。React 会用 `requestIdleCallback` 询问浏览器主线程是否空闲。(后续换成了 Scheduler)
3. work loop 负责执行这个安排。它需要追踪下一个 `unitOfWork`，以及主线程剩余的时间。
4. 在这个例子中，下一个 `unitOfWork` 是 button 元素。它读到了当前 `list` 元素上的 `update` 对象，然后在 `WIP`（workInProgress）Fiber 上标记 `flags`。
5. button 被 bailout，继续处理下一个 `unitOfWork`：item1。item1 也被 bailout，没有变化。
6. 还有剩余时间，处理 item2：比较后标记 `flags`。它的子元素 `div` 比较后也有变化，同样标记 `flags`。item3 同理。
7. item2、item3 会把自己的 `flags` 合并到父节点上，这就是 `effect list`，如图：

   ![effect list](/static/images/Fiber/effectList.png)

8. 然后进入 Phase 2：Commit，遍历 `effect list` 操作 DOM，最后修改 `fiberRoot.current` 的指向。

## 优先级

但这样只是让浏览器主线程可以分多步完成工作，并不能解决渲染耗时长导致页面卡顿的问题。
所以还需要引入优先级（Priority），主要分为 6 种：

1. Synchronous：和 Stack Reconciler 差不多，同步执行
2. Task：在 next tick 之前执行
3. Animation：在 next frame 之前执行
4. High：尽快执行
5. Low：允许少量延迟
6. Offscreen：为显示或滚动做准备

假设现在还有另一个紧急按钮，我们先点击 `^2`，再点击紧急按钮。当浏览器主线程有空闲时，React 会直接从 `HostRootFiber` 开始，
先处理紧急按钮带来的工作，相当于丢弃了 `^2` 已经做了一半的工作。

## 生命周期函数

我们知道，生命周期函数并不都在同一阶段执行。

Phase 1：

1. componentWillMount
2. componentWillReceiveProps
3. shouldComponentUpdate
4. componentWillUpdate

Phase 2：

1. componentDidMount
2. componentDidUpdate
3. componentWillUnmount

所以一些生命周期函数可能不会按我们预想的顺序触发。
通常我们认为 `componentWillUpdate` 和 `componentDidUpdate` 是成对调用的，
但遇到刚才说的优先级抢占时，就可能出现不一样的结果：

```text
start update 1      componentWillUpdate

start update 2      componentWillUpdate
                    componentDidUpdate
re-start update 1   componentWillUpdate
                    componentDidUpdate
```
